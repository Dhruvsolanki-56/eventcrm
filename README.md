# Gather CRM

Gather is a capture-first CRM built with React, Vite, TypeScript, Express, and SQLite. Its main path is: choose or take a business-card photo, upload immediately, review the resulting lead one at a time, save it, optionally edit/send an email, and continue to the next card. Selecting an image starts the upload and read job; there is no separate Scan button. QR codes are also checked on-device. After “Save person,” each user can choose “Ask every time” (the default) or “Never ask” in the account menu; the preference is private to that user and workspace. “Save & scan next” always prioritizes the next card.

## Run locally

The workspace UI now uses a compact professional layout with a light sidebar, restrained green actions, flat panels, and consistent sans-serif typography. `/analytics` adds live date/event-filtered activity, unique people and companies, current company deal values, quality/stage breakdowns, event comparisons, recent-person links, refresh, and daily CSV export. It is available to company admins/managers and private-space owners. See [UI_REDESIGN.md](docs/UI_REDESIGN.md) for the data definitions and reference designs; analytics values come from accessible stored encounters rather than placeholder charts.

Requires Node.js 22 and npm. From this directory:

```powershell
Copy-Item .env.example .env
npm ci
npm run seed
npm run dev
```

Open `http://localhost:5173`. The development sign-in screen has sample accounts for two exhibitor workspaces (admin, manager, representative) and two private attendee spaces. The seeded password is `Gather-Demo-2026!` unless `DEMO_PASSWORD` is set before seeding. Do not use seeded accounts or the development server for real customer data.

The Northstar sample workspace has 12 companies, 30 people, six company-level deals, encounters across two events, varied follow-ups and meeting states, and draft/accepted/failed/replied email examples. All names and addresses are synthetic. The email examples are labeled sample data; “accepted” describes the fixture state, not inbox delivery. A development-only Settings action lets the current admin/owner clear sample records and their private media by typing `CLEAR`; it preserves the login, memberships and every other workspace. Synthetic upload-ready PNGs are bundled under `public/demo/`: a card, a brochure containing a valid QR website link, and a standalone QR code. Three synthetic spoken WAV fixtures are also bundled with matching manually entered transcripts. Seeding copies them to each demo workspace's private uploads area; authorized playback works, while cross-workspace requests are denied. The transcript status is `manual`, not speech-provider output. On Windows with Python `pywin32` and Microsoft Zira SAPI installed, regenerate them with `python scripts/generate-demo-audio.py`.

For a production-mode local smoke run, configure `.env` with persistent absolute paths for `DATABASE_PATH`, `UPLOADS_PATH`, and `BACKUPS_PATH`; set `NODE_ENV=production`, `HOST`, `PORT`, `PUBLIC_BASE_URL` (HTTPS), and appropriate provider settings. Then run:

```powershell
npm run build
npm start
```

The service serves the built frontend and API from one Node process. Put it behind a correctly configured TLS reverse proxy on a single VM with local persistent storage. Keep exactly one application writer/worker; do not put SQLite/WAL on network storage. Linux systemd, Caddy, and daily local/off-VM backup templates are included in [DEPLOYMENT.md](docs/DEPLOYMENT.md); they have not been installed or verified on a VM. Account verification and password recovery are implemented, but production SMTP, DNS/provider credentials, automated secret provisioning, release rollback, and external monitoring are not configured or tested. Do not expose public sign-up until those operational controls are staged and reviewed.

## Configuration

See `.env.example`. Important settings:

- `DATABASE_PATH`, `UPLOADS_PATH`, `BACKUPS_PATH`: persistent writable paths; keep uploads/backups out of the public web root.
- `NODE_ENV`, `HOST`, `PORT`, `TRUST_PROXY_HOPS`: runtime and proxy settings. Use HTTPS at the proxy in production so secure cookies are honored.
- `PUBLIC_BASE_URL`: canonical HTTPS origin used for unsubscribe links.
- `AI_MODE`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`: provider calls require both `AI_MODE=provider` and a provider key. `AI_MODE=off` always keeps card reading, email suggestions, and follow-up suggestions on manual/template paths, even if a key is present. Demo reading is enabled only for the test environment. The configured default `claude-sonnet-5` is listed as active in Anthropic's [model status documentation](https://docs.anthropic.com/en/docs/about-claude/model-deprecations) as checked on 2026-09-30; recheck provider availability and run real-card evaluations before release. No live OCR provider call was tested here.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM_NAME`, `SMTP_FROM_ADDRESS`: optional Nodemailer transport. With no configured SMTP, Send stores an explicitly unsent outbox item. With SMTP configured, acceptance by the mail server is not proof of delivery. On 2026-09-30 Gmail accepted one real, one-time test message sent from and to the configured demo mailbox. This verifies SMTP authentication and provider acceptance only; inbox delivery remains unverified. For a private Gmail demo, configure `SMTP_HOST=smtp.gmail.com`, the account's app password, and a permitted From address in the untracked `.env`; do not paste credentials into chat or commit them.
- `DEMO_EMAIL_ADDRESS`: non-production default for both the editable From address and the editable Settings test recipient. It defaults to `dhruvtube11@gmail.com` in `.env.example`; this is an address only, not working SMTP authentication. Changing the From field does not change a lead's recipient.
- `PUBLIC_BASE_URL`: must be the canonical HTTPS origin in production; password recovery and email verification links use one-time, expiring fragments. Production signup is refused before account creation if SMTP or the HTTPS origin is unavailable. The automated mail fixture test verifies account confirmation and recovery locally; it does not verify a real mailbox.
- `REQUIRE_EMAIL_VERIFICATION`: test-only switch used by the local SMTP E2E fixture to exercise required verification outside production. Production always requires verification.
- `SMTP_REQUIRE_TLS`: defaults to `true`; set to `false` only for a deliberately local SMTP fixture or a provider that documents a non-TLS local transport. Do not disable it for production SMTP.
- `DEMO_PASSWORD`: development seed password only. Seeding is refused when `NODE_ENV=production`.
- `NOTE_STORAGE_WORKSPACE_LIMIT_BYTES`, `NOTE_STORAGE_TOTAL_LIMIT_BYTES`, `NOTE_COUNT_WORKSPACE_LIMIT`, and `NOTE_COUNT_TOTAL_LIMIT`: transactional text-note byte and count caps (defaults: 16 MiB and 100,000 notes per workspace; 512 MiB and 500,000 notes across the service). A successful text note also writes an audit row. Production note creation is additionally limited to 120 saves per member per hour using the single process's rate-limit store; that rate window resets on process restart, while the durable storage caps remain in force.
- `VOICE_STORAGE_WORKSPACE_LIMIT_BYTES` and `VOICE_STORAGE_TOTAL_LIMIT_BYTES`: raw recording byte caps; `VOICE_NOTE_COUNT_WORKSPACE_LIMIT` and `VOICE_NOTE_COUNT_TOTAL_LIMIT`: durable lifetime creation caps (defaults: 25,000 notes per workspace and 100,000 service-wide); `VOICE_TRANSCRIPT_WORKSPACE_LIMIT_BYTES` and `VOICE_TRANSCRIPT_TOTAL_LIMIT_BYTES`: aggregate manual transcript byte caps (defaults: 16 MiB per workspace and 512 MiB service-wide). Voice count counters are not replenished by deleting notes. These application limits reduce storage amplification but do not guarantee host disk capacity; use filesystem quotas, monitoring, backups, and a retention policy too.
- `TASK_COUNT_WORKSPACE_LIMIT` and `TASK_COUNT_TOTAL_LIMIT`: transactional caps for follow-up and meeting rows, including closed records (defaults: 25,000 per workspace and 100,000 across the service). Each accepted task creates an audit row in the same SQLite transaction. Production task creation is additionally limited to 120 saves per member per hour using the single process's rate-limit store; this in-memory rate window resets on restart, while durable caps remain in force. These row caps reduce unbounded task growth; they do not replace host disk alerts or a filesystem quota.

Camera capture requires a secure browser context (HTTPS, or localhost) and camera permission. On phones, Capture offers a separate single-photo `Take photo` picker (`capture="environment"`) for a quick rear-camera photo, plus `Choose photos` for multiple images. To test that picker on a phone: put the phone and development computer on the same trusted Wi-Fi, run `npm run dev`, find the computer's LAN IPv4 address, then open `http://<computer-LAN-IP>:5173` on the phone. Allow the development server through the computer's private-network firewall if prompted, sign in with a sample account, and tap `Take photo`; upload and reading run through the local development service. A LAN HTTP page is not a secure context, so the browser's live viewfinder may be unavailable there. To test `Open camera` or automatic QR watching from the viewfinder, use a trusted HTTPS development URL (or localhost on that device) and grant camera permission. Do not expose the development server to an untrusted network or enter real contact data during this test. Voice notes require microphone permission and a supported browser recording format. Transcription is not configured; recordings stay playable and accept text entered by the user.

## Commands

```powershell
npm run seed                 # update development sample fixtures; never production
npm run dev                  # API and Vite development servers
npm test                     # unit tests, including provider and auth failure handling
npm run test:e2e             # seed fixtures and run browser journeys
npm run test:mail             # local SMTP protocol fixture; no external email is sent
npm run test:manual-reading   # no-provider upload, honest manual fallback, and phone save
npm run test:scan-quota       # malformed/oversized uploads are rejected safely
npm run test:note-quota       # workspace and shared text-note byte caps, with rollback checks
npm run test:note-count-quota # workspace and shared text-note count caps
npm run test:task-quota      # follow-up workspace/service caps with no-partial-write checks
npm run test:task-rate       # per-member follow-up burst limit and independent-member check
npm run test:voice-quota     # durable voice-recording counts and aggregate transcript bytes
npm run test:e2e -- tests/e2e/shell.spec.ts # seeded routes, including private demo audio authorization
npm run audit                # seed fixtures and run the route/layout audit
npm run audit:controls       # click distinct visible actions and internal links in both workspaces/layouts
npm run audit:controls:phone # same crawl at 390 px only
npm run test:ops              # offsite backup path, checksum and retention safety tests
npm run generate:demo-media   # regenerate synthetic card, brochure, and valid QR PNGs
npm run build                # client and server type checks plus production build
npm run test:production-smoke # rebuild and smoke-check the built server in an isolated temp folder
npm start                    # serve dist/ and /api from the Node service
npm run backup               # online SQLite database backup
npm run backup:offsite        # requires a configured rclone remote; copies, downloads and verifies before local pruning
npm run restore -- <file>    # integrity-check backup and restore with a recovery copy
```

`npm run backup` creates a timestamped bundle under `BACKUPS_PATH` containing an online SQLite snapshot, the private uploads tree, and SHA-256 checksums in `manifest.json`. Because SQLite and media files cannot share one cross-filesystem transaction, schedule full bundles during a short write-maintenance window for a point-in-time-consistent pair. `npm run restore -- <bundle-directory>` checks the database and media checksums, refuses to proceed when active SQLite WAL/SHM sidecars exist, stages both resources, and preserves any previous database/media directories as recovery copies. Legacy single-file SQLite backups can still be restored, but do not include media. The `ops/systemd/gather-backup.timer` template schedules a daily run at 03:17 with a randomized delay, and the offsite wrapper keeps a bounded local set, pruning only after remote read-back verification succeeds. These templates are not installed here; remote encryption and lifecycle retention depend on the selected provider and remain unverified. A local isolated test verified restored SQLite integrity and a media fixture; an actual VM-level backup/restore drill remains open.

## Included routes and workflows

Frontend routes: `/home`, `/setup`, `/scan`, `/review/:scanId`, `/people`, `/people/:contactId`, `/companies`, `/companies/:companyId`, `/pipeline`, `/reports`, `/follow-ups`, and `/settings`. First-time setup can be resumed from the account menu; its state is private to the signed-in user and workspace. The setup test goes to the signed-in account; the Settings test goes to its editable test-recipient address. Both report mail-server acceptance, never inbox delivery. Unauthenticated screens also handle `/reset-password` and `/verify-email`; tokens are carried in URL fragments so browsers do not send them in HTTP request paths. Unknown routes get a not-found screen. The attendee view hides company pipeline and reports. API routes cover authentication and account recovery/verification, workspace/dashboard, scans and QR, people/companies and admin company merge, company deal fields, reports/CSV, workspace JSON export (including available private media), notes/voice, email drafts/send/status/retry/unsubscribe, per-user capture preferences and setup progress, settings, private-space data deletion, follow-ups, and job retry/problems; exact route declarations are in `server/index.ts`.

The schema and matching code maintain one company per contact within a workspace, normalize company names/domains to avoid duplicates, show accessible company suggestions during review, offer same-person confirmation for matching email/phone, and record repeat scans as encounters. Admins can combine duplicate companies with typed confirmation; people and brochures move to the company kept, old names/domains remain matching aliases, and merging two records with deal details is refused for manual reconciliation. The People search searches accessible companies and people together and links directly to either record. Company deal value is stored on the company. Contact review exposes only name, company, email, phone, job title, and website, with compact optional note, quality, products, and follow-up fields. On a phone, the uploaded image can be enlarged and the save actions remain reachable while scrolling. Home's next-step card follows the current work: it links to the next ready review, due follow-ups, missing personalization details, or capture, in that order. Today's capture and due-follow-up counts use the active event's time zone; the latter counts follow-up tasks rather than meetings.

People can be archived and restored without removing notes, encounters, voice recordings, or email history; archived people leave active lists and dashboard metrics. Permanent delete is a separate typed-confirmation action for private-space owners and company admins, and removes the person’s dependent history and media while retaining the shared company. Workspace exports retain archived records and archive/restore audit events. The seeded browser regression verifies archive, hidden active detail, restore, preserved history/audio, and export audit evidence.

A complete source security scan of the 112-file snapshot on 2026-09-30 reported one medium finding: authorized workspace members could create text notes without an aggregate byte/count bound, growing the shared SQLite database and audit log. The route already limited each note to 4,000 characters and checked workspace/contact access, but repeated requests were not bounded. The fix adds transactionally enforced per-workspace and service-wide byte/count limits plus a per-member production rate limit. `npm run test:note-quota` and `npm run test:note-count-quota` exercise workspace/shared boundaries and verify rejected writes do not alter notes, audit rows, or contact versions. The report is source-based, not production certification; one independent baseline reviewer participated, but an independent architecture reviewer could not start because the agent-thread limit was reached, so that pass was done by the primary reviewer.

A later partial security scan of the unversioned 116-file snapshot on 2026-09-30 found one medium issue: authenticated members could create follow-ups without a durable aggregate row limit. The fix applies workspace and service-wide task-count caps inside the transaction that writes both task and audit rows, plus a production per-member rate limit. `npm run test:task-quota` passed and verified workspace/service rejection with no task or audit changes on rejected requests. That source review predates the fix, had partial coverage, and is not a post-remediation security certification.

The most recent partial source review found an event-boundary gap in contact notes: a member who could access a shared contact could see or mutate another event's voice notes. Notes now record their creator and, when available, the accessible encounter. Event-scoped members see notes they created or notes linked to an event they can access; only the creator or a workspace admin can change or delete a voice note. Legacy unlinked notes without a known creator remain visible to admins/private-space owners rather than being guessed into an event. A browser regression checks hidden text and audio, direct audio download, text changes, deletion, and draft context. That source review predates this fix and is not post-fix certification.
